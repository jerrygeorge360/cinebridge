# Data and security contract

**Stage:** Data and security contract (Stage 6)

**Status:** Draft for the explicit human architecture gate. This document does not record approval.

This contract turns the approved PRD, architecture, decisions, and responsive Penpot-flow evidence into constraints for later implementation. It is a design artifact only: it adds no credentials, application code, endpoints, or product behavior to the repository.

## 1. Non-negotiable invariants

- The product remains one independently deployable repository with a Next.js web application, a FastAPI API, SQLAlchemy, and one persistent SQLite instance.
- Qloo is called only by FastAPI. Qloo credentials are deployment secrets; they never enter the browser, SQLite, this repository, request bodies returned to customers, or logs.
- Public registration and private management use different high-entropy bearer tokens and different route scopes. Possession of the public token cannot authorize management access.
- A public response never contains attendee display names, attendee preferences, recommendation inputs, private-token material, management counts, or selection state.
- MVP management responses expose aggregate coverage and recommendation/selection results, not a public or organizer-facing attendee list. The backend may use private preference rows during recommendation processing.
- A recommendation is either backed by real, validated provider data or is reported as limited/unavailable. The system never invents a film, substitutes a fabricated provider response, or silently reuses a result from a different audience snapshot.
- The organizer makes the final film choice. There is no automatic announcement and no screening-rights verification claim.
- All timestamps are stored as UTC instants. The event screening date is a date-only value; it is validated against the API's calendar date and is not converted through a browser timezone.

## 2. Domain schema

The first domain migration creates the following tables. Names are logical names; the implementation may use SQLAlchemy naming conventions while preserving the fields, constraints, and privacy classifications.

### `events`

One row per organizer-created screening event.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID represented as SQLite `TEXT`, primary key | Generated by the backend; never derived from a bearer token | Internal identifier |
| `name` | `TEXT NOT NULL` | Trimmed, NFC-normalized, 1–120 characters | Public event metadata |
| `theme` | `TEXT NOT NULL` | Trimmed, NFC-normalized, 1–120 characters | Public event metadata |
| `screening_date` | `DATE NOT NULL` | Valid ISO date and a future calendar date at creation | Public event metadata |
| `essential_details` | `TEXT NOT NULL` | Trimmed, NFC-normalized, 1–1,000 characters | Public event metadata |
| `created_at` | UTC timestamp, `NOT NULL` | Server-generated | Internal metadata |

The event row contains no raw public or private token. Event metadata is intentionally shareable through the public registration link, but the API must return only the fields needed for registration.

### `event_access_tokens`

Separate bearer credentials for the two access scopes.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Internal identifier | Internal identifier |
| `event_id` | Foreign key to `events.id`, `NOT NULL` | Delete with the event | Internal identifier |
| `purpose` | `TEXT NOT NULL` | Exactly `public_registration` or `private_management` | Secret metadata |
| `token_digest` | Fixed-size `TEXT` or `BLOB`, `NOT NULL` | HMAC-SHA-256 digest using a deployment-provided hash secret; never the raw token | Secret-derived value |
| `digest_version` | Short `TEXT NOT NULL` | Allows a future key-rotation migration | Secret metadata |
| `issued_at` | UTC timestamp, `NOT NULL` | Server-generated | Internal metadata |
| `revoked_at` | Nullable UTC timestamp | Reserved for operational revocation; null means active | Secret metadata |

Constraints:

- There is at most one active token of each purpose per event, and `token_digest` is indexed and unique among active credentials.
- The backend generates each raw token with at least 32 cryptographically secure random bytes and encodes it as an unpadded URL-safe value.
- The raw token exists only while constructing the one-time event-creation response and its corresponding link. It is not written to SQLite, application logs, analytics, error reports, or durable browser storage by the API.
- Token lookup hashes the presented value with the expected purpose's digest version and compares digests in constant time. A public route never attempts private-token authorization, and vice versa.
- The MVP has no automatic token expiry or self-service token recovery. Reissuing a token requires an explicit future product/operations decision because the original raw value cannot be reconstructed from its digest.

### `attendees`

One row per public registration submission. There is no attendee account or email identity in the MVP.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Backend-generated | Private identifier |
| `event_id` | Foreign key to `events.id`, `NOT NULL` | Delete with the event | Private relationship |
| `display_name` | `TEXT NOT NULL` | Trimmed, NFC-normalized, 1–80 characters | Private personal data |
| `created_at` | UTC timestamp, `NOT NULL` | Server-generated | Private metadata |

Each submission creates one attendee row. No IP address, user-agent, cookie value, or browser fingerprint is stored with the attendee.

### `attendee_preferences`

Zero to three optional favorite-title entries for an attendee.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Backend-generated | Private identifier |
| `attendee_id` | Foreign key to `attendees.id`, `NOT NULL` | Delete with the attendee | Private relationship |
| `position` | Small integer, `NOT NULL`, check 1–3 | Stable display/input slot | Private metadata |
| `title_text` | `TEXT NOT NULL` | Trimmed, NFC-normalized, 1–160 characters; this is the attendee's supplied title, not a claimed Qloo match | Private preference |
| `enjoyed_text` | Nullable `TEXT` | Trimmed, NFC-normalized, 0–500 characters | Private preference |
| `created_at` | UTC timestamp, `NOT NULL` | Server-generated | Private metadata |

There are no rows for blank favorite slots. A title is required for a used slot; the explanation may be blank. The unique key `(attendee_id, position)` and a maximum of three rows enforce the product limit. Raw preference text is never sent to a public endpoint or persisted in a log.

### `recommendation_runs`

One immutable record of each backend recommendation attempt for an event.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Backend-generated | Private identifier |
| `event_id` | Foreign key to `events.id`, `NOT NULL` | Delete with the event | Private relationship |
| `status` | `TEXT NOT NULL` | `succeeded`, `limited`, or `unavailable` | Private result metadata |
| `registered_count` | Non-negative integer, `NOT NULL` | Snapshot used for coverage messaging | Aggregate private data |
| `usable_preference_count` | Non-negative integer, `NOT NULL` | Snapshot of attendees with usable input, not raw preferences | Aggregate private data |
| `represented_attendee_count` | Non-negative integer, `NOT NULL` | Snapshot used for coverage warnings | Aggregate private data |
| `warning_code` | Nullable short `TEXT` | Stable product-safe code such as `limited_coverage` | Private result metadata |
| `failure_code` | Nullable short `TEXT` | Internal classification; never a provider payload | Restricted operational data |
| `algorithm_version` | Short `TEXT NOT NULL` | Identifies the policy version used | Internal metadata |
| `requested_at` | UTC timestamp, `NOT NULL` | Server-generated | Private metadata |
| `completed_at` | Nullable UTC timestamp | Server-generated | Private metadata |

The run stores counts and status, not attendee names, raw preference text, Qloo credentials, raw Qloo requests, or raw Qloo responses. A run with `succeeded` or `limited` status and customer-visible candidates has exactly three candidate rows. An `unavailable` run has zero candidate rows.

### `recommendation_candidates`

Validated, provider-backed candidate snapshots belonging to a run.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Backend-generated | Private identifier |
| `run_id` | Foreign key to `recommendation_runs.id`, `NOT NULL` | Delete with the run | Private relationship |
| `rank` | Small integer, `NOT NULL`, check 1–3 | `1` is the top pick; `2` and `3` are alternatives | Private result metadata |
| `provider_entity_id` | Nullable bounded `TEXT` | Provider identifier retained only to support selection/audit; never required in customer responses | Restricted provider data |
| `title` | `TEXT NOT NULL` | Validated provider title, max 200 characters | Product result |
| `release_year` | Nullable four-digit integer | Validated if supplied | Product result |
| `runtime_minutes` | Nullable positive integer | Validated if supplied | Product result |
| `content_rating` | Nullable bounded `TEXT` | Validated if supplied | Product result |
| `languages` | Nullable bounded serialized list | Allowlisted, size-limited values only | Product result |
| `fit_explanation` | `TEXT NOT NULL` | Plain-language explanation, max 1,000 characters | Product result |
| `warning_text` | Nullable `TEXT` | Plain-language limitation/warning, max 500 characters | Product result |

The unique key `(run_id, rank)` prevents duplicate positions. No raw provider score is persisted for cross-query comparison. If the policy uses multiple Qloo ranking queries, positions are normalized within each query before any audience weighting; incomparable raw affinity scores are never combined.

### `selections`

At most one organizer choice for an event.

| Field | Type/constraint | Notes | Classification |
| --- | --- | --- | --- |
| `id` | UUID, primary key | Backend-generated | Private identifier |
| `event_id` | Foreign key to `events.id`, `UNIQUE`, `NOT NULL` | Enforces one final choice in the MVP | Private relationship |
| `run_id` | Foreign key to `recommendation_runs.id`, `NOT NULL` | Must contain the selected candidate | Private relationship |
| `candidate_id` | Foreign key to `recommendation_candidates.id`, `NOT NULL` | Must belong to `run_id` and be rank 1–3 | Private result reference |
| `selected_at` | UTC timestamp, `NOT NULL` | Server-generated | Private metadata |

Selection is private management data. It does not create an announcement, ticket, rights record, or attendee notification.

## 3. Access-token and endpoint boundary

The browser calls only the FastAPI product API over HTTPS. Next.js may render the public or private experience, but it does not query SQLite or Qloo directly. Route names below describe the boundary to implement; they are not implemented by this stage.

| Boundary | Input | Allowed response | Must never return |
| --- | --- | --- | --- |
| Event creation | Event fields from an unauthenticated organizer | One-time public registration link and one-time private management link, plus non-sensitive event metadata | Attendee data, Qloo data, credential values, raw token outside the links needed for creation |
| Public event read | Public token in the path | Event name, theme, screening date, and essential details needed to register | Private token, registration count, coverage, attendee rows, preferences, recommendations, selection |
| Public registration | Public token plus display name and zero to three preference entries | Generic success acknowledgement only | Echoed preferences, attendee ID, counts, management link, recommendation state |
| Private overview | Private management token in the path | Event metadata, aggregate registration/coverage counts, safe status and selection summary | Public-token material, attendee names, raw preferences, Qloo payloads or credentials |
| Private recommendation request/read | Private management token and a bounded request | Recommendation status; on success/limited, exactly one top pick and two alternatives with explanations/warnings; on failure, an honest unavailable result | Raw attendee inputs, raw provider scores/requests/responses, invented or stale fallback films |
| Private selection | Private management token plus a candidate from a valid run | Confirmation of the selected provider-backed candidate | Public announcement, attendee contact data, screening-rights assertion |

Rules applying to every boundary:

- Token-bearing routes use path parameters rather than query parameters. Access logs and error reports redact the entire token-bearing segment, not only part of it.
- Invalid, revoked, wrong-purpose, and nonexistent tokens have the same generic not-found/unauthorized behavior. Responses must not reveal whether an event or the other token scope exists.
- Management data is never made available through a public token, and no public endpoint accepts a private token as an alternate credential.
- The API sets a restrictive referrer policy for token-bearing pages and does not send token-bearing URLs to third-party services. The API has no analytics payload containing bearer links.
- The public response shape is deliberately aggregate/minimal. A later request to expose raw attendee preferences, attendee names, or a new sharing scope is a material privacy decision and must be recorded in `docs/DECISIONS.md` before implementation.

## 4. Validation and request limits

Validation occurs in FastAPI before persistence and before any Qloo call. The web client may provide early feedback but is not a trust boundary.

### Input rules

- Accept JSON only for write operations, require the expected content type, and reject malformed JSON, unknown top-level fields, null bytes, control characters, and values outside the limits below.
- Trim leading/trailing whitespace and normalize Unicode to NFC before checking length. Store plain text; do not interpret input as HTML or Markdown.
- Count user-visible characters for text limits, and enforce a separate encoded request-body limit so repeated or malformed fields cannot bypass field limits.
- `event.name`: 1–120 characters.
- `event.theme`: 1–120 characters.
- `event.screening_date`: `YYYY-MM-DD`, a real calendar date, and a future date at creation.
- `event.essential_details`: 1–1,000 characters.
- `attendee.display_name`: 1–80 characters.
- `attendee_preferences`: zero to three entries; each `title_text` is 1–160 characters and each `enjoyed_text` is optional and at most 500 characters.
- Event creation and registration JSON bodies are at most 16 KiB; management request bodies are at most 8 KiB. Response sizes are bounded by the three-candidate contract.
- Provider data is validated against the same bounded result model before it reaches a customer response or the database. Unexpected provider fields are ignored; missing required candidate data makes the result unavailable rather than being filled in.

### Rate-limit points

Rate limiting is enforced at the API boundary before the corresponding database or Qloo work. The following are safe MVP defaults for the single API instance; implementation may tune them downward, but materially loosening them requires a recorded decision.

| Operation | Limiting keys | Default limit |
| --- | --- | --- |
| Event creation | Source address and global instance | 5 per 15 minutes per source; 100 per minute globally |
| Public event read | Source address and public-token digest | 60 per minute per key |
| Public registration | Source address + public-token digest, and public-token digest | 10 per 10 minutes per source/event; 100 per hour per event |
| Private overview/recommendation read | Source address + private-token digest | 60 per minute per key |
| Recommendation request | Private-token digest | 3 per 10 minutes per event; this protects Qloo and SQLite |
| Selection | Private-token digest | 10 per minute per event |

The limiter may be process-local and bounded in memory while the product is intentionally single-instance. Its keys are HMACs of the source address and token digest using a deployment secret; raw addresses and raw tokens are not persisted. Entries expire within one hour. If a trusted reverse proxy is introduced, forwarded-address headers are honored only from explicitly configured proxy hops; caller-supplied headers are not trusted by default. A rate-limited response is generic, returns `429`, and may include a bounded `Retry-After` value without revealing event existence.

## 5. Logging, privacy, and retention

### Logging rules

Structured operational logs may contain a request ID, route template, method, status class, latency, response size, rate-limit result, and coarse recommendation outcome. They must not contain:

- raw public or private tokens, token-bearing URLs, authorization headers, cookies, referrer values, or token digests;
- request or response bodies;
- attendee display names, favorite titles, enjoyment text, or other free text;
- Qloo credentials, raw Qloo requests/responses, provider error bodies, or raw provider scores;
- a full database row, stack trace containing request data, or a URL copied from a customer link.

Errors returned to customers are generic and safe. A server-side classification may record `qloo_timeout`, `qloo_rate_limited`, `qloo_invalid_response`, or `qloo_unavailable`, but it must not include provider payloads or secret material. Film titles and explanations are product data and should not be logged by default.

### Retention defaults

These are proposed MVP defaults and require human approval at this stage's gate:

| Data | Retention |
| --- | --- |
| Raw attendee rows and preference rows | Delete 30 days after the event screening date |
| Event metadata, token digests, recommendation summaries/candidates, and selection | Delete 180 days after the event screening date |
| Operational and security logs | Delete after 30 days |
| In-memory rate-limit entries | Expire within one hour |
| Raw Qloo request/response material | Never persist; clear from request memory after processing |

Deletion is an event-scoped, transactional purge: preferences before attendees, recommendation candidates before runs, selections and access tokens before the event row, with foreign-key cascades as a safety net. The purge must not be implemented by deleting arbitrary database files. Any operator backup or export must honor the same retention policy; indefinite backups are not a reason to retain application data indefinitely.

The contract does not add accounts, analytics, email, cookies for identity, or a separate personal-data warehouse. Application-level encryption at rest is not claimed here; deployment storage and HTTPS remain operational concerns and must not be represented as product guarantees unless configured and verified.

## 6. Qloo boundary and failure contract

The Qloo adapter is backend-only and receives the minimum normalized interest information necessary for the approved recommendation policy. It does not receive public/private tokens, event links, display names, IP addresses, venue details, or arbitrary attendee metadata. Enjoyment explanations remain backend data and are included in provider calls only if a later approved adapter contract explicitly requires them.

Before persistence or response, the backend validates provider identifiers, titles, eligibility metadata, and result cardinality. It applies event and film eligibility constraints before ranking, normalizes positions within each Qloo query, and uses attendee representation for weighting. It never combines incomparable raw affinity scores across queries.

The observable contract is:

| Condition | Stored status | Customer result |
| --- | --- | --- |
| At least three real, eligible, validated candidates and normal coverage | `succeeded` | Exactly one top pick and two alternatives, with explanation and relevant warnings |
| At least three real, eligible, validated candidates but low/partial coverage | `limited` | Exactly one top pick and two alternatives, clearly labeled as limited; show represented/registered coverage and do not imply guaranteed enjoyment |
| Timeout, network failure, provider 4xx/5xx, provider rate limit, credential/configuration failure, malformed response, no eligible candidate, or fewer than three valid candidates | `unavailable` | No candidate cards and no invented film; say recommendations are unavailable/limited and permit a bounded retry or more-input path |

An unavailable response does not silently serve a previous run, a hard-coded film, or a partial list that would look like a complete shortlist. A retry creates a new run snapshot. Provider failures are not allowed to expose whether a credential is missing or which upstream status occurred. The organizer-facing copy must preserve the design language that CineBridge supports the decision but does not guarantee enjoyment or verify screening rights.

## 7. Migration approach

- Add the first domain schema through a versioned SQLAlchemy migration tool; Alembic is the intended implementation choice. No application table is created by startup side effects, and no schema is part of the setup checkpoint.
- The initial migration creates the seven tables above, foreign keys, uniqueness/check constraints, and indexes for token digests, event relationships, preference slots, run ordering, and the one-selection-per-event constraint.
- Enable SQLite foreign-key enforcement on every connection. Keep the database on the existing persistent `/data` volume and preserve the one-instance deployment boundary.
- Migrations are forward-only and tested against both a fresh database and the immediately previous schema. Use an expand/backfill/contract sequence for later changes; destructive drops, token-digest changes, and retention changes require a reviewed migration and backup/rollback plan.
- A digest-secret rotation cannot recover raw historical tokens. It requires a versioned secret and an explicit token reissue/revocation plan before it is attempted.
- Migration application must complete before the API serves traffic for that revision. It must not require the neighboring development-factory repository, external services, or Qloo availability.
- There is no existing domain data to backfill from the setup checkpoint. If a future migration needs to transform attendee or recommendation data, it must preserve the privacy and retention rules in this document and include a bounded, restartable data migration.

## 7a. Optional programming and artwork providers

- DeepSeek and TMDB keys are backend-only deployment secrets. They are never returned to Next.js, persisted in SQLite, or included in logs.
- The agent receives only a bounded, already-ranked candidate summary and no attendee names or raw preference text. It may inspect the shortlist and make at most one current-information search; source URLs/dates are product evidence, while Qloo affinity remains separately labelled.
- Store only the compact brief, tool names, token/cost/latency counters, and source metadata. Do not store model prompts, model chain-of-thought, raw search responses, or raw provider errors.
- TMDB fields are limited to verified ID, poster path, and lookup time on the candidate snapshot. A title/year mismatch or unavailable provider yields no artwork, never a guessed image.
- DeepSeek/Search/TMDB failure does not change deterministic shortlist eligibility or rank and must not make provider configuration details visible to an organizer.

## 8. Human decisions required at the architecture gate

The following items are intentionally surfaced for human review; the coordinator does not approve them:

1. Approve or revise the proposed retention windows: 30 days for raw attendee data after the screening date, 180 days for event/result data, and 30 days for logs.
2. Approve the deployment-secret-backed HMAC token-digest treatment and the rule that the MVP has no self-service token recovery.
3. Approve the proposed default rate limits and the process-local limiter, which relies on the already-approved single-instance architecture.
4. Confirm that aggregate management coverage and recommendation results are sufficient for the MVP and that raw attendee preference rows remain backend-only rather than being exposed in the organizer UI.

No item above changes the approved architecture silently. If any is rejected, update `docs/DECISIONS.md` and this contract before Stage 7 (Event and access foundation) begins.
